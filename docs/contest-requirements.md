## 省赛与国赛的必交材料

官方赛项详情在省赛、国赛两节列出的材料清单一致。晋级后仍需完成国赛报名和对应阶段的作品提交。最终应以报名账户内该赛项的实际字段和组委会后续通知核对上传方式。[赛项材料要求](https://www.boxuegu.com/matchTrack/detail/?id=10039) [官方赛程通知](https://www.boxuegu.com/matchNotice/)

### 1. 代码仓库与完整演进记录

- [ ] 提供 GitHub 或 Gitee 仓库地址。
- [ ] 仓库设为公开，或为评审提供有效访问权限。
- [ ] 源码与最终演示、PDF、README 所述版本相符。
- [ ] 保留完整、细粒度的 Git 提交历史，每次提交对应真实的核心 AI 对话或功能迭代。
- [ ] 检查提交历史能够追踪从功能雏形、修复到最终结果的演进。

赛项明确要求原创作品，禁止将已有开源项目直接包装参赛，并禁止使用一个包含全部功能的初始提交代替开发演进历史。使用通用第三方依赖时，应保留其实际许可证和来源，并准确说明复用范围。[代码仓库、原创性及演进要求](https://www.boxuegu.com/matchTrack/detail/?id=10039)

### 2. AI 对话历史与至少三条核心 Prompt 链

- [ ] 保存至少 3 个核心功能迭代的完整 Prompt 链。
- [ ] 每条链包含真实的提问、AI 建议或修改、用户或代理的后续引导，以及功能结果。
- [ ] 对真实遇到的故障，保留问题表现、修复对话和验证结果。
- [ ] 导出 AI 工具的对话历史。工具不支持导出时，可保存截图或录屏。
- [ ] 为各条链标明对应功能、实际时间、相关 Git 提交及验证证据，便于评审交叉核对。

官方要求至少 3 个核心功能的完整交互链，内容包括 Prompt、AI 修改建议和引导 AI 修复 Bug 的过程。上述时间、提交和验证索引是本项目拟采用的证据组织方法。[AI 开发记录要求](https://www.boxuegu.com/matchTrack/detail/?id=10039)

记录应直接来源于实际开发。材料整理可以补充摘要、索引和解释，开发时间、用户原话、AI 回答和故障结果须与原始记录一致。预先设计的功能提示词应标为计划，采用后再附上真实执行记录。

### 3. README 复现性声明与 10 分钟重现指南

- [ ] 写明支持的操作系统、浏览器、Node.js 版本及其他真实前置条件。
- [ ] 提供完整安装、启动和访问命令，并附依赖清单和锁定文件。
- [ ] 给出实际使用的环境变量模板及各变量含义。
- [ ] 提供演示输入文件、操作顺序和可核对的预期结果。
- [ ] 从干净副本执行实际复现，记录耗时和环境。
- [ ] 验证依赖安装、启动和核心演示流程能在目标 10 分钟内完成。

官网将完整环境配置、依赖清单、环境变量模板和 10 分钟极速复现指南列为要求。环境变量的具体内容应由最终实现决定。复现耗时只能报告实测结果。[README 与复现要求](https://www.boxuegu.com/matchTrack/detail/?id=10039)

### 4. 演示视频

- [ ] 用户完成真实录屏，最终视频为 MP4、1080p。
- [ ] 总时长为 5 至 8 分钟。
- [ ] 至少 2 分钟用于 AI 协同过程的复现展示。
- [ ] 展示最终版本中真实可用的核心功能及输入输出。
- [ ] AI 协同片段能够看到 Prompt、生成或修复过程，以及对结果的实际验证。
- [ ] 对照最终文件核实格式、分辨率、总时长和 AI 片段时长。

上述格式和时长来自省赛、国赛的演示视频要求。官网举例包括输入 Prompt 生成核心模块，或引导 AI 解决实际 Bug。[视频要求](https://www.boxuegu.com/matchTrack/detail/?id=10039)

本项目由用户实际录制。我方提供可照着操作的分镜、讲解稿、演示数据、操作顺序和对应 AI 记录位置。拟将视频安排为约 6 至 7 分钟，为 AI 协同部分预留约 2 至 3 分钟。最终脚本须根据已验证的作品调整。

### 5. PDF 技术文档

- [ ] 文件为 PDF，页数不超过 30 页。
- [ ] 说明作品面对的真实问题、使用者、主要场景和解决流程。
- [ ] 重点说明意图控制策略，包括上下文如何组织、Prompt 如何设计、约束如何传递。
- [ ] 说明架构设计、模块职责、数据流及对 AI 生成代码的约束方式。
- [ ] 给出可复现性论证，链接 README、输入样例、真实开发记录和验证证据。
- [ ] 截图、功能描述、测试结果和版本号与最终作品一致。
- [ ] 列出实际采用的第三方组件、依赖、来源和许可证。
- [ ] 逐页渲染并检查中文字体、表格、图片、页码和分页。

官网明确要求 PDF 不超过 30 页，重点覆盖意图控制策略、架构设计和可复现性论证。问题定义、第三方来源及逐页检查用于补全本项目的可理解性和交付质量。[PDF 技术文档要求](https://www.boxuegu.com/matchTrack/detail/?id=10039)

建议文档按以下内容组织，篇幅随实际成果安排。

1. 作品概述与使用场景。
2. 需求和可验收目标。
3. 数据导入、检查、清洗、图表和导出的实际流程。
4. 架构、数据结构和操作记录设计。
5. 至少三轮 AI 协作的目标、关键交互、改进及证据索引。
6. 可复现性、真实验证结果及适用边界。
7. 第三方依赖、引用和后续改进。

## 当前实现范围与验收边界

当前技术决策采用 React、TypeScript 和 Vite。拟实现浏览器本地的 CSV、TSV、XLSX 导入，数值质量检查，清洗与撤销重做，ECharts 拟合图表，以及报告、操作记录导出。此处记录的是本项目范围与决策，完整功能仍需逐项实现和验证。

最终验收应通过正常界面验证以下完整流程。

- [ ] 从本地选择真实 CSV、TSV、XLSX 文件，核对表头、行数和导入值。
- [ ] 使用包含缺失、重复、数值格式和异常值的数据，核对定位结果及检测依据。
- [ ] 执行清洗操作，核对受影响的行、列和结果。
- [ ] 执行撤销和重做，核对数据、图表和操作历史的一致性。
- [ ] 使用已知关系的实验数据，核对 ECharts 图形、拟合参数和数值结果。
- [ ] 导出报告、处理后的数据及操作记录，重新打开文件并核对内容。
- [ ] 以最终仓库版本完成一次新环境复现，再准备最终截图、视频脚本和 PDF。

界面截图、单元测试和样例通过各自证明实际覆盖的部分。完整业务流程尚未经过真实浏览器验证时，应保留待验证状态。PDF 和视频中的每项功能陈述应能够对应到最终可运行版本。
